S/4HANA Release Upgrades: Building Regression Test Automation Remotely

JJ
Joseph Jose
Founder & CEO, niogod™

Most S/4HANA programmes concentrate their testing effort on the go-live: integration tests, user acceptance, cutover rehearsals. Then the system enters normal life, and the testing burden does not disappear. Every feature pack, every release upgrade, every larger transport and every change to an interface carries regression risk across finance, logistics and production. In many Mittelstand companies, that regression testing still falls on key users who also run the daily business. A remote engineering team can build and operate automated regression testing for SAP, provided the company defines the business-critical processes, provides stable test data and keeps the go or no-go decision in-house.

The migration wave is cresting

The DSAG Investment Report 2026, based on 198 member companies surveyed between December 2025 and January 2026, shows the shift. S/4HANA on-premises is now installed at 56 percent of respondents, up from 44 percent in 2024, while SAP ECC and older Business Suite installations fell from 68 to 54 percent. Of those still planning, 37 percent intend to switch by the end of 2027, the date on which SAP's mainstream maintenance for ECC ends; extended maintenance runs to the end of 2030. In other words, a large group of companies is entering the operate phase of S/4HANA in the next two years, with a regular upgrade rhythm ahead of them.

Testing capacity has not kept pace. Bitkom's September 2026 labour market study found that only 9 percent of companies use AI in software testing so far, with a further 16 percent considering it, and 6 percent of companies with IT vacancies are searching specifically for QA and test profiles. SAP test automation engineers who also understand the business processes are a niche within that niche.

What to automate first

Automating everything is neither possible nor useful. Start with the processes where a defect would stop revenue, production or the closing.

PriorityProcess examplesWhy
1Order to cash, procure to pay, production order to goods receiptHigh volume, direct impact on revenue and supply
2Financial close steps, intercompany postings, tax determinationErrors surface late and are costly to correct
3Interfaces to MES, warehouse, e-commerce, banks, e-invoicingChanges on either side break silently
4Custom developments and key Fiori appsMost likely to be affected by upgrades and clean core changes

The building blocks

Process catalogue

A list of business-critical end-to-end processes, each described by key users as steps with expected results. This is the specification for automation and the shared language between business and the remote team.

Test data strategy

Automated tests need stable master data: customers, materials, vendors, prices and bank details that exist in the test system and do not change between runs. The most robust pattern is a dedicated, synthetic test data set created by script after every system copy. Using a copy of production data is common but brings personal data into the test landscape, which then needs the same protection as production, including when a remote team works on it.

Tooling

The choice of tool depends on the landscape and licences: SAP's own test tools, commercial test automation suites or open frameworks for Fiori and API tests. More important than the tool is a modular design, in which reusable building blocks such as create sales order or post goods receipt are combined into process tests, so that one change in the system requires one change in the tests.

Execution and reporting

Tests run on a schedule and on demand after transports into the quality system. Results are reported per process with a clear status for the change advisory board. A remote team can run nightly suites in the German night, so results are ready at the start of the business day.

Who owns what

  • Business process owners and key users define processes and expected results, and approve changes to the catalogue.
  • SAP basis and the internal team provide system copies, transports and authorisations.
  • The remote team builds and maintains the automation, the test data scripts and the reporting, analyses failures and separates genuine defects from test maintenance.
  • The release manager decides go or no-go based on the results.

Common stumbling blocks

Three patterns slow down test automation in SAP landscapes particularly often. First, unstable test systems: if the quality system is copied or reconfigured without coordination, runs fail for reasons unrelated to the software. A shared calendar for system copies and maintenance windows prevents this. Second, missing authorisations: technical test users need exactly the roles of real users, otherwise the suite tests a process nobody performs that way. Third, an unmaintained catalogue: if the business changes a process without updating the catalogue, the automation keeps testing the old version.

Acceptance criteria for a sprint-based contract

Test automation suits a Werkvertrag or a sprint-based Leistungsbeschreibung well because its output is measurable. Useful criteria include the number of catalogue processes automated and stable across a defined number of runs, the share of failures correctly classified within one working day, the runtime of the full regression suite within an agreed window, and documentation that lets the internal team run the suite without the supplier. Each sprint is then accepted (Abnahme) against these criteria.

An illustrative ramp-up

In the first two months, the team automates the five to ten most critical processes and establishes the test data scripts. Over the following quarter, coverage grows to the agreed catalogue and the suite is integrated into the transport process. From then on, maintenance aligns with the release calendar: before each upgrade, the suite is extended for new functions and run repeatedly in the sandbox. The timing is an example; landscapes with many custom developments take longer.

The data protection remarks above are general information and not legal advice; the use of production data in test systems should be agreed with your data protection officer.
