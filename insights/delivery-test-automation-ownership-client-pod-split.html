Who Owns the Tests? Splitting Test Automation Between Client and Pod

JJ
Joseph Jose
Founder & CEO, niogod™

When an external pod builds part of your product, test automation often falls into a gap. The pod writes unit tests because its engineers are used to it; your team expects end-to-end coverage but never specified it; acceptance testing happens manually the day before the sprint review. The result is slow Abnahme, recurring regressions and arguments about whether a defect was "in scope". The remedy is a written ownership model that assigns each test layer to one side, defines what "done" means for each, and makes the results part of the acceptance evidence.

The problem in numbers

Test automation is a known weak spot across the industry. The World Quality Report 2024, published by Capgemini, Sogeti and OpenText from a survey of more than 1,750 senior executives in 33 countries, found that 57 percent of organisations cite the lack of a comprehensive test automation strategy as a key barrier. The same report found that 68 percent are using generative AI in quality engineering or have roadmaps after successful pilots, which raises the volume of code and tests without solving the strategy question.

The cost of weak quality is large and cumulative. CISQ's 2022 report estimated the cost of poor software quality in the United States at USD 2.41 trillion and the accumulated technical debt at around USD 1.52 trillion. These are US figures, but they describe a structural effect: defects not caught by tests turn into operational cost and into debt that slows every later sprint.

Staffing does not offer an easy way out. In Bitkom's 2026 study of the German IT labour market, QA and testing roles were sought by only 6 percent of companies with IT vacancies, far behind operations and software development. Testing is rarely the role DACH teams hire for first, which is one reason it ends up undefined in external contracts. And AI-assisted coding adds pressure: in the Stack Overflow Developer Survey 2025, 45 percent of developers said debugging AI-generated code is time-consuming.

A layer-by-layer ownership model

The principle is simple: whoever writes the code writes and maintains the automated tests for it, while the client keeps control over what the acceptance scenarios are. This keeps the pod accountable for quality of its own work and keeps the definition of "correct" with the party that will accept it.

Acceptance scenarios belong to the client

The acceptance layer is where most disputes start, so specify it with care. Under a Werkvertrag, the client declares Abnahme (BGB §640) when the work substantially conforms to what was agreed. If the agreed criteria are vague, acceptance becomes a negotiation. A practical pattern:

  1. The client's product owner writes acceptance criteria per story in a structured form, for example given, when, then.
  2. The pod turns each criterion into an automated test before or during implementation and links the test to the story.
  3. Criteria that cannot reasonably be automated are marked as manual and listed in the sprint review agenda.
  4. The sprint's Abnahme package contains the test run results for every story, plus the manual check results.

This turns acceptance from an opinion into a report. It also makes change visible: if a criterion changes after the test was written, that is a change request, not a defect.

Guardrails that keep the suite healthy

  • Flaky test budget. A test that fails intermittently is quarantined within one working day and fixed or removed within the sprint. A suite people ignore protects nothing.
  • Runtime budget. The pull request suite stays under a fixed limit, for example 15 minutes, so that engineers in both time zones get feedback within a working session.
  • Test data ownership. Synthetic test data is generated and versioned by the pod. Production extracts are not used in automated tests unless anonymised under a process your data protection officer has approved.
  • Coverage as a signal, not a target. Track coverage of changed code per pull request rather than a global percentage, which tends to reward trivial tests.
  • Regression for every escaped defect. When a bug reaches staging or production, the fix includes a test that would have caught it.

When the client already has a QA team

Many Mittelstand organisations have an internal QA function or a test centre with established tools. In that case, do not duplicate it. Agree that the pod delivers unit, integration and contract tests within its own pipeline, while the client's QA team owns system and end-to-end testing in its environment. The interface between the two is the release candidate and a short handover note listing what changed and what the pod has already verified. The important point is that each layer has exactly one owner.

Checklist for the Leistungsbeschreibung

  • Test layers and owners written down, as in the table above.
  • Definition of done per story includes passing automated acceptance tests.
  • Gate rules: which failures block merge, which block release.
  • Flaky test and runtime budgets agreed.
  • Test data rules aligned with data protection requirements.
  • Test results included in every sprint's Abnahme package.
  • Ownership of the suite on contract exit: the client receives the full suite and its documentation.

This article is general information and does not constitute legal advice; acceptance and data protection terms in your contract should be reviewed by qualified counsel.

Test ownership is ultimately a question of accountability: the side that builds should prove the work, and the side that accepts should define what proof means. In the niogod™ pod, the Senior Consultant owns the quality gates and the test evidence that goes into each sprint's Abnahme under the Werkvertrag. If test responsibility in your external delivery is still implicit, it is worth making it explicit before the next contract period.
