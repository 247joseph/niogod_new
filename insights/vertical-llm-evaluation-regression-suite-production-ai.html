LLM Evaluation Before Release: Building a Regression Suite for Production AI

JJ
Joseph Jose
Founder & CEO, niogod™

Most AI features in DACH products do not fail in the demo. They fail three releases later, when a prompt change, a model version upgrade or a new retrieval index quietly degrades answers that used to be correct, and nobody notices until a customer does. The answer is not more manual testing. It is an evaluation regression suite that runs on every change, the same way unit tests do for deterministic code, with a small set of metrics the product owner has agreed to in advance.

Why this has become a release problem, not a research problem

Adoption has moved faster than engineering discipline. Bitkom reported in September 2026 that 57 percent of German companies with 20 or more employees now use AI, up from 36 percent a year earlier, and 11 percent already use AI agents. The same survey found that nine in ten companies see themselves at the beginning of their AI use. That combination, broad deployment with immature practice, is exactly where regressions slip through.

The pilot to production gap is also well documented. Omdia's 2025 AI Market Maturity Survey, reported in November 2025, found that 31 percent of firms saw fewer than 5 percent of their AI proofs of concept reach operational use, and only 9 percent moved more than half into production. One recurring reason is that teams cannot show, release after release, that the system still behaves as specified. Capital is not the constraint: KfW Research counted EUR 6.3 billion invested in German AI start-ups between January and September 2026, roughly double the full 2025 figure. The constraint is engineering capacity that knows how to make probabilistic systems releasable.

What an evaluation regression suite actually contains

A useful suite is a versioned asset in the repository, not a notebook on someone's laptop. It has four parts.

  1. A golden dataset. Between 200 and 1,000 real or realistic inputs, each with an expected outcome or grading rubric, stratified by use case, language (German and English separately) and difficulty. Every production incident adds at least one case.
  2. Graders. Deterministic checks first (schema validity, required fields, forbidden content, citation present), then reference-based metrics where an answer key exists, and only then model-based grading with a fixed judge model and a fixed rubric prompt.
  3. Thresholds. Agreed pass rates per slice, for example "structured extraction above 97 percent field accuracy, German answers no worse than English by more than 3 points". Thresholds belong in the Leistungsbeschreibung if an external team builds the feature.
  4. A pipeline hook. The suite runs in CI on every pull request that touches prompts, retrieval configuration, model version or tool definitions, and blocks the merge if a threshold drops.

Decision framework: which grader for which output

Output typePrimary graderTypical threshold logicMain risk
Structured extraction (JSON, forms)Field-level exact or normalised matchPer-field accuracy, hard floorSilent schema drift after model upgrade
Classification and routingConfusion matrix against labelsPrecision and recall per classMinority classes collapsing
Retrieval-augmented answersRetrieval hit rate plus faithfulness checkContext recall, unsupported claim rateIndex changes that remove sources
Free text generationRubric-based model grading, sampled human reviewMean score plus share below minimumJudge model bias and drift
Agents with tool callsTrajectory checks: correct tool, arguments, orderTask success rate, unsafe action rate of zeroSide effects in connected systems

A step sequence for the first six weeks

  1. Week 1: Inventory every place a model output reaches a user or another system. Rank by business impact. Pick the top three for the first suite.
  2. Week 2: Build the golden dataset from production logs (pseudonymised, with a documented legal basis) and from domain experts. Label 300 cases. Write the expected outcome before running the model, not after.
  3. Week 3: Implement deterministic graders and the first reference metrics. Record a baseline on the current production configuration.
  4. Week 4: Add model-based grading for open text. Calibrate the judge against 50 human-graded cases and record the agreement rate. If agreement is weak, fix the rubric before trusting the score.
  5. Week 5: Wire the suite into CI. Define what blocks a merge and what only warns. Publish a one-page report per run.
  6. Week 6: Run a deliberate regression drill: swap the model version or degrade the retrieval index and confirm the suite catches it.

Common failure patterns

  • Testing on the prompt author's examples. The person who writes the prompt should not write all the test cases. Separation of authorship is the cheapest quality control available.
  • A single aggregate score. An average hides a collapse in one slice. Always report by language, customer segment and task type.
  • Unpinned judge models. If the grading model changes, scores move without the product changing. Pin versions and re-baseline deliberately.
  • No cost and latency budget. A change that improves quality by 2 points but doubles token cost or pushes p95 latency past the UX limit is a regression. Track both alongside quality.
  • Evaluation without ownership. Someone must own the dataset. Unowned golden sets decay within a quarter.

How this connects to governance

An evaluation suite is not a compliance programme, but it produces the evidence a compliance programme needs: documented test data, defined metrics, versioned results and a record of what changed between releases. For teams whose systems may later fall into a regulated category, building that discipline now is far cheaper than reconstructing it from logs. It also makes external delivery measurable: a sprint is accepted when the suite passes at the agreed thresholds, not when a demo looks convincing.

Checklist before the next model upgrade

  • Golden dataset versioned, with owner and last review date
  • Baseline scores recorded for the current production configuration
  • Thresholds per slice, signed off by product
  • Judge model pinned and calibrated against human grades
  • Cost per request and p95 latency tracked in the same report
  • CI blocks merges on threshold breach
  • Rollback path tested within the last month

Evaluation work is steady, specification-driven engineering, which makes it well suited to a team that is measured on accepted increments rather than hours.
